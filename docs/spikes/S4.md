## 2. Wake time: `sysctl -n kern.waketime` / `kern.sleeptime`

All exit 0, unprivileged, `/usr/sbin/sysctl`:

```
$ /usr/sbin/sysctl -n kern.waketime
{ sec = 1795094890, usec = 792285 } Thu Nov 19 22:28:10 2026
$ /usr/sbin/sysctl -n kern.sleeptime
{ sec = 1795094415, usec = 254500 } Thu Nov 19 22:20:15 2026
$ /usr/sbin/sysctl -n kern.boottime
{ sec = 1794807763, usec = 121948 } Mon Nov 16 14:42:43 2026
$ /usr/sbin/sysctl kern.waketime kern.sleeptime kern.boottime
kern.waketime: { sec = 1795094890, usec = 792285 } Thu Nov 19 22:28:10 2026
kern.sleeptime: { sec = 1795094415, usec = 254500 } Thu Nov 19 22:20:15 2026
kern.boottime: { sec = 1794807763, usec = 121948 } Mon Nov 16 14:42:43 2026
```

Format (fixed): `{ sec = <epoch seconds>, usec = <microseconds> } <ctime local>`,
one line ending in `\n`, no tabs (`od -c` checked). `sec` is Unix epoch seconds
(UTC), directly comparable with `/bin/date +%s` (`now` was `1795106746`).

Cross-check with `pmset -g log` (same values):

```
2026-11-19 22:20:13 +0900 Sleep               	Entering Sleep state due to 'Maintenance Sleep':TCPKeepAlive=active Using Batt (Charge:61%) 478 secs
2026-11-19 22:28:11 +0900 Wake                	Wake from Deep Idle [CDNVA] : due to smc.sysState.Wake(0x70070000) lid SMC.OutboxNotEmpty RTP.multi-touch/HID Activity Using BATT (Charge:61%)
```

`kern.wake_abs_time` 4743810660712 and `kern.sleep_abs_time` 4743809309403
differ by 56 ms of Mach time: Mach absolute time stops during sleep, so
these are no use for "seconds since wake" in sh; use the calendar `sec`.

Dark wakes: whether a DarkWake (lid shut, maintenance) also updates
`kern.waketime` was not observable (no dark wake happened after the last
sleep). [INFERENCE: yes; xnu sets `gIOLastWakeTime` when the root domain
returns to its ON state, and a dark wake is that state with reduced
capabilities.] Either way the grace only delays one restore by at most 60 s.

### Seconds since last wake in POSIX sh

Tested with `/bin/sh`, `/bin/dash`, `/bin/bash`, `/bin/zsh`; all printed
`waketime_sec=1795094890 now=1795106918 since_wake=12028`:

```sh
w=$(/usr/sbin/sysctl -n kern.waketime 2>/dev/null)
w=${w#*sec = }
w=${w%%,*}
case $w in ''|*[!0-9]*) w= ;; esac
now=$(/bin/date +%s)
since=
[ -n "$w" ] && [ "$w" -gt 0 ] && since=$((now - w))
```

Parser robustness (`/bin/dash`):

| Input | Extracted `w` |
| --- | --- |
| `{ sec = 1795094890, usec = 792285 } Thu Nov 19 22:28:10 2026` | `1795094890` |
| `{ sec = 0, usec = 0 } Thu Jan  1 09:00:00 1970` (fabricated: never slept since boot [INFERENCE]) | `0` |
| empty | empty |
| `garbage` | empty |

### Wake grace rule for T4 (C7 step 3)

Skip the stale-claim restore only when `0 ≤ now − w < WAKE_GRACE`. When `w` is
empty or 0, or `now − w` is negative (wall clock set backwards), apply no grace
and continue to `restore stale-claim`. A negative age must not grant a grace,
or a clock moved back by hours would block the restore for hours. Reading is
cheap (median 6.6 ms).

Why the grace is needed: the claim age is wall-clock time, and wall-clock time
runs during sleep while Herdr's timers do not, so after any sleep longer than
`STALE` (45 s) the claim is stale until Herdr's next tick (≤ 10 s, or 30 s in
the keeper branch). launchd.plist(5) on this Mac: "If the system is asleep
during the time of the next scheduled interval firing, that interval will be
missed", so the daemon fires again within one `StartInterval` (15 s) after
wake; 60 s covers both.
